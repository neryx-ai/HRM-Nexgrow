# Plan: Probar envío de correos SMTP sin afectar a usuarios reales

## Contexto

Actualmente el sistema tiene **5 puntos de disparo** de correos (welcome, reset password, colillas de pago) usando Nodemailer v8. Las variables SMTP **no están configuradas** en `.env`, por lo que el sistema está en modo "sandbox" de facto: registra los correos en logs pero no los envía.

## Problema

El usuario quiere **probar el envío real por SMTP** para iterar, pero **sin que los correos lleguen a los usuarios reales** del sistema.

---

## Solución propuesta

### 1. Añadir `SMTP_TEST_EMAIL` — variable de redirección universal

Nueva variable de entorno opcional que, cuando está presente, redirige **TODOS** los correos salientes a una única dirección de prueba.

**Comportamiento:**
- Si `SMTP_TEST_EMAIL=miemail@test.com` está seteada → todos los correos van a esa dirección
- El subject se prefija con `[TEST → destinatario@original.com]` para trazabilidad
- Si no está seteada → comportamiento normal (envío a destinatarios reales)
- Si SMTP no está configurado → igual que antes (log + no enviar)

### 2. Arreglar bug en `.env`

La línea 2 de `.env` tiene `BETTER_AUTH_URL` duplicado (debería ser `BETTER_AUTH_SECRET`). Corregir.

### 3. Actualizar `.env.example`

Añadir `SMTP_TEST_EMAIL` documentado.

## Cambios necesarios

### `src/lib/email.ts` — `sendEmail()` (línea 51-97)

Añadir lógica de redirección al inicio de la función, después de validar config:
```typescript
const redirectTo = process.env.SMTP_TEST_EMAIL;

if (redirectTo && redirectTo !== to) {
  logger.info("EMAIL", `[TEST MODE] Redirigiendo correo de ${to} → ${redirectTo}`);
  return sendEmail({
    to: redirectTo,
    subject: `[TEST → ${to}] ${subject}`,
    html,
    text,
  });
}
```

**Nota:** Se usa recursión directa para reaprovechar toda la lógica existente (transporter, error handling, logging). La condición `redirectTo !== to` evita loop infinito si el test email coincide con el destinatario original.

## Cómo usarlo

1. Configurar las 5 variables SMTP en `.env` (host, port, user, pass, from)
2. Añadir `SMTP_TEST_EMAIL="mi-correo-personal@gmail.com"`
3. Ejecutar cualquier acción que dispare un correo (crear usuario, reset password, finalizar planilla)
4. Todos los correos llegarán a la dirección de prueba, con el subject mostrando el destinatario original
5. Para habilitar envío real: simplemente quitar `SMTP_TEST_EMAIL` del `.env`

## Riesgos / Consideraciones

- **Sin cambios en callers:** Solo se modifica `email.ts`. Los 5 callers (`user.actions.ts`, `empleado.actions.ts`, `planilla.actions.ts`, `auth.ts`) no requieren cambios.
- **Colillas de pago masivas:** Si se finaliza una planilla con muchos empleados, TODOS los correos irán al email de prueba. Es el comportamiento deseado para testear, pero puede generar muchos emails de golpe.
- **El email de prueba recibe datos sensibles** (contraseñas temporales, enlaces de reset, datos de planilla). Usar un email personal controlado.
- **Sin cambios en BD ni migraciones** requeridas.
